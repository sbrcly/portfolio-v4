## 1. Prompt Lab

### What it is

The Prompt Lab is the admin tool at `/admin/prompt-lab` that stores, versions, edits, previews and publishes the system prompts, model knobs and output-gate thresholds for the app's governed AI surfaces, with a read-only sibling at `/admin/ai-outputs` that shows what those surfaces have produced. It exists so prompts can change without a deploy or an App Store build, so every generation can be traced to the exact prompt version that produced it, and so a bad edit can be rolled back by moving a pointer. It is used by whoever holds the admin flag, which the evidence suggests is only Scott. Eleven AI surfaces, served from nine call sites, read their prompt through it at call time. Without it nothing user-facing breaks: the read path falls back to in-code producer functions that are proven byte-identical to the seeded prompts. What would be lost is editing without deploying, version history, rollback, and the version id stamped on each row of the generation ledger.

### Architecture

**Routes.** One client page with four tabs (Surfaces, Fragments, Groundings, Phrase lists) and a detail modal, 23 files under `app/(dashboard)/admin/prompt-lab`. The API is 19 route files under `app/api/admin/prompt-lab`, in three parallel groups for surfaces, fragments and groundings: list, detail, version history and save-draft, discard-draft, and publish (which also performs rollback when given an older version id). Surfaces add a preview route; fragments and groundings add an impact-review route. A read-only phrase-lists route and one AI Outputs route complete the set.

**Data model.** Three entity and version pairs: `PromptSurface` with `PromptSurfaceVersion`, `PromptFragment` with `PromptFragmentVersion`, `PromptGrounding` with `PromptGroundingVersion`. Versions are immutable, append-only, full text rather than deltas, and carry an author (an admin id or one of two system sentinels for seed and code refresh), a required note, and a set-once first-published timestamp. Each entity has a nullable unique pointer to its active version. Only surface versions carry knobs (model purpose, temperature, max tokens, retry max tokens, a thresholds JSON object), so one pointer flip moves body, knobs and thresholds atomically. The seed shape is 11 surfaces, 13 fragments, and 26 groundings (13 denomination keys times two grounding modes, content and posture). Alongside sit `PromptFallbackEvent`, `AIGeneration` (the generation ledger) and `AIUsageEvent` (token telemetry). States are derived, never stored: active is whatever the pointer targets, historical is published and not active, draft is never published and not active; one open draft per entity, otherwise a conflict.

**How a version becomes what the model sees.** A call site asks `getSurfaceConfig(surfaceKey, denomination)` in `lib/prompts/prompt-readpath.ts`. The read path keeps a per-instance in-memory cache with a 60 second TTL and stale-while-revalidate, loads cold in one batched set of three queries, and holds the in-flight reload at module scope so it outlives the request. Assembly (`lib/prompts/prompt-assembler.ts`) is a single-pass substitution of exactly two kinds of template token: one grounding slot, filled with theology text chosen by the user's denomination and the surface's pinned grounding mode (an unknown denomination falls to a creedal baseline), and named fragment slots for shared voice text. No recursion, no conditionals. Two sanity checks follow: a minimum length and no surviving placeholder. The database stores a model purpose name, never a raw model id; the call site maps purpose to model through `lib/ai/models.ts`. Publish invalidates the local cache after commit; other instances converge within the TTL.

**Fallback.** A nine-value reason taxonomy covers database error, empty config, a 250 millisecond cold-read budget exceeded, missing surface, grounding or fragment, null grounding, and the two sanity failures. On any of them the read path returns the in-code producer for that surface plus code-side knob and threshold defaults (`lib/prompts/prompt-knobs.ts`), never throws, logs a structured warning, bumps an in-memory counter, and appends a `PromptFallbackEvent` row without awaiting it. The Surfaces list shows a seven-day fallback count and the last reason per surface.

**Preview.** `lib/prompts/prompt-preview.ts` assembles the active rows for a chosen denomination and deliberately never falls back; it returns one of five structured unresolved reasons so a broken configuration is visible rather than masked.

**Publish guards.** A surface publish re-validates the stored version (schema, body composition, must assemble for the baseline denomination) and flips the pointer in a transaction. A fragment or grounding publish fans out to every surface that includes it, so it requires an impact review: the server returns before-and-after assembled prompts for every dependent plus a SHA-256 digest over the version id, the draft text, and the sorted dependents with their active pointers; the publish recomputes the digest inside the transaction and writes only on exact match and only if no dependent newly fails to assemble (`lib/admin/prompt-lab-impact.ts`, `prompt-lab-digest.ts`).

**History and diffs.** Version history lists newest first; any two versions can be diffed. The diff view is a line diff of the full text plus a key-by-key diff of knobs and thresholds. The impact review modal diffs the assembled prompt per dependent surface.

**Drift.** The drift badge in the UI is a provenance test, not a text comparison: "diverged" means the active version was authored by an admin rather than by the seed or code-refresh sentinel. A true byte comparison of served database text against the in-code producer exists only in command-line tools: `scripts/export-prompts.ts` (which also writes prompts to files for review) and `scripts/refresh-grounding.ts`.

**Snapshot tests.** Six check scripts, 1,145 lines, all in the local `pnpm type-check` chain and none in CI (the only GitHub workflow is a signup canary; the build command does not chain them):

- voice snapshot: two shared voice constants against two golden text files;
- seed snapshot: per surface, the expected placeholder composition, and assemble(seed data) equals the producer output byte for byte across 11 surfaces times 13 denominations, 143 cells (comments still cite 169 from when there were 13 surfaces);
- read-path fallback: the same 143 cells through the real read path with an injected loader and zero fallbacks, then seven forced failure cases, the cold timeout, and warm-after-background-reload;
- knob snapshot: seeded knobs and thresholds equal the code defaults for all 11 surfaces;
- preview: 12 assertions over the healthy and five unresolved states;
- impact gate: 22 assertions over digest determinism, order insensitivity, stale acknowledgement, and save validators.

The important caveat: these prove that the seed module equals the producers in code. They never read a live database, so they cannot say whether production has drifted from either.

**Model routing.** `lib/ai/models.ts` maps purposes to four tiers. The Haiku tier serves journal reflection, activity framing, theme tagging and three classifiers. The Sonnet tier serves prayer generation, weekly reflection, Bible reflection, synthesis, drill-down prayer, the reveal, pattern interpretation, the admin commitment tools and vision extraction (an environment flag can route extraction to Opus). The Opus tier serves eight admin content drafters. OpenAI appears as a failover for Bible reflection and photo extraction and as speech-to-text for prayer transcription. For governed surfaces the purpose is a database-editable knob; the tier-to-model mapping stays in code.

**Cost telemetry.** `AIUsageEvent` records input, output, cache-creation and cache-read tokens per call (`lib/ai/usage-telemetry.ts`). No dollar cost is computed anywhere, and no code in the repo reads the table; it is write-only from the application's point of view. The generation ledger (`lib/ai/generation-ledger.ts`) writes one `AIGeneration` row per model call: surface key, prompt version id or fallback reason, resolved model, a seven-value outcome (success, truncated, gate-rejected, parse failure, model skip, error, fallback output), reason, the raw model output before parsing or gating, a user id without a foreign key, and wall time. Inputs are never stored; retention is 90 days via a cleanup cron. The analytics Operational tab shows counts, outcomes and median latency per surface; raw text is never shown in any UI.

**How output quality is judged.** `lib/prompts/insight-voice.ts` holds 30 banned phrases, 8 coach phrases and 8 refusal prefixes with gate functions for empty output, a skip token, refusal prefixes, coach voice, banned phrases, a length floor and ceiling with graceful truncation, surveillant and second-person openers, sentence termination, and leaked user names. Thresholds are per-surface knobs. The weekly reflection adds a two-attempt loop that appends the rejection reason to the retry, a quote-aware scan, refusal detection with no retry, and soft "retry-only" reasons kept on the last attempt. Eval-like tools exist but are human-judged: a weekly reflection sampler that runs the real prompt, model and gates through a read-only seam and writes to gitignored files; a 44-sample prayer evaluation matrix with automated checks where the owner's reading is the acceptance gate; and a side-by-side model comparison for the reveal surface. There is no automated scorer or model-as-judge. The AI Outputs page reads nine persisted governed surfaces from their domain tables with 30-day counts, status counts over 7 and 30 days, failure reasons, and paginated output records with user ids truncated to eight characters and no join to inputs.

**The surfaces.** The eleven governed keys are Bible reflection, drill-down prayer, journal reflection, pillar prayer, pillar scripture, synthesis, prayer generation, onboarding prayer generation, reveal, weekly reflection and insight observation. Two more (pillar act and pillar fast) were in the registry until 2026-07-17; `git show` confirms 13 at commit 0e4b9103 (2026-06-08) and 11 at b1190cf5. Stale "13 call sites" comments remain in the schema and one check script, and 13 is also the denomination count, a likely source of confusion. Four feature flags in `lib/constants/aiLayerFlags.ts` are off, and by their comments three governed surfaces (synthesis, pillar prayer, journal reflection) do not dispatch today, so at most eight governed surfaces generate in production (inferred from flag comments, not traced per call site). Beyond the governed set: nine ungoverned user-facing call sites with inline prompts, ledgered under `ungoverned:*` keys (act and prayer category inference, act connection, activity-log framing, Bible photo extraction, journal insight, prayer sensitivity inference, prayer summary, theme tagging); eleven admin drafters under the admin API (commitments three, discovery three, lectionary two, memory verse, prayers, teaching) that write no ledger rows though ten record token usage; and one speech-to-text call with no prompt. Roughly 9 of about 30 logical model call sites read a versioned prompt.

### The hard parts

1. **Moving prompts into a database without changing a byte.** The seed was derived from the producers, and the 143-cell identity matrix plus an omitted-fragment check prove the two agree. A senior engineer would ask what stops them drifting later; the answer is the local check chain, not CI.
2. **A read path that can never fail a generation.** Budgeted cold read, stale-while-revalidate, module-scope reload, a typed fallback taxonomy, and forced-failure tests. The question is cross-instance invalidation; the answer is that there is none, by design, with 60 second convergence.
3. **Fan-out edits.** One fragment edit rewrites many live prompts. The digest-bound impact review and the in-transaction recompute make the review and the publish refer to the same world; a race returns a conflict.
4. **The fallback shadowing an edit.** After an admin edit, an outage serves pre-edit code text. Mitigations are an explicit caveat in both publish modals, durable fallback events and the drift badge. The obvious question is why the last published version is not snapshotted back into code; it is not.
5. **Code moving ahead of the database.** `reports/GROUNDING_REFRESH_REPORT.md` documents placeholder grounding text being served for nine traditions (18 rows across two modes) because the seed writer updated a legacy column the read path no longer read, while the badge said "in sync". The fix was a guarded refresh tool with dry run, optimistic pointer check, receipts, and a second system sentinel. Whether it was applied to production is unknown.
6. **Observability without storing user text.** The ledger stores outputs only, is awaited on background paths and non-blocking on the two user-awaited paths, and tolerates a missing column during deploy windows.

## 2. Analytics dashboard

### What it is

The analytics dashboard at `/admin/analytics` is a read-only internal view answering whether the product is being used, by whom, and whether the plumbing is healthy: practice activity, retention, subscriptions, onboarding, notifications, cron health, the AI pipeline, per-user drill-down and creator link visits. Access is the shared admin gate; every one of its 26 routes calls `requireAdmin`, and none accepts a write. It is presumably used only by Scott. Nothing user-facing depends on it; removing the page and routes would break no user flow. What the app does for it is the reverse: an activity ledger of surface opens, a cron-run table, an acceptance timestamp on partner links, a direct-purchase enum on subscription transitions, and client events added specifically so the dashboard could count them. The shared `lib/analytics` folder also holds 16 client event-emitter modules that the app imports, so the folder is not deletable even if the dashboard were.

### Architecture

**Page and tabs.** One client page with state in URL parameters. Six top-level tabs (Today, Product, Business, Operational, Users, Creators); Product has ten sub-tabs (overview, pray, prayers and creeds, lectio, lectionary, people, bible, scripture, journal, reflection), for 15 views. Operational embeds notifications and onboarding; Reflection embeds the older Insights tab. Five retired tab ids redirect.

**Routes and data sources.** 26 route files, all GET: today, subscription, operational, notifications, onboarding, onboarding funnel, scripture, journal stats, insights, comprehensive insights, user insight details, filter options, eight product routes, four user routes (one dynamic by user id), and two creator routes. Data comes from Postgres through Prisma and from PostHog through a server-side HogQL bridge (`lib/analytics/posthog-bridge.ts`) with a ten-minute Redis cache, an eight-second timeout, and a result union that never throws; without Redis configured it runs uncached. Billing data arrives as RevenueCat webhook rows already in Postgres. Read path: tab component, TanStack Query (48 call sites), a fetch wrapper, the route, `requireAdmin`, the demo fork, a user-filter resolver (internal roster plus eight filter dimensions), counts-only modules in `lib/analytics`, pure folds, JSON.

**Metric definitions, each defined once.**
- Presence (`lib/analytics/presence.ts`): a user is present on a Pacific day if any of eight legs has a row: prayer, scripture or legacy activity logs excluding onboarding-origin rows; a journal entry; a Sunday lectionary read; a weekday reading; a Bible chapter read to its end; a verse highlight, note or favorite; a People request sent or an in-app "I prayed"; and the activity ledger of surface opens, which credits presence but no pillar. Bare app opens and push opens deliberately do not count. A `PresenceDefinition` component is the tooltip twin of the code.
- DAU is the mean of distinct present users per Pacific day; today's partial day is shown beside the same hour yesterday.
- Weekly Return and Reading Reach use completed Monday-to-Sunday weeks only and drop weeks whose denominator is under five.
- Retention: D1 is the exact day; D7, D14 and D30 use a three-day window ending on day D; onboarded signups only.
- Comeback: a gap of seven or more days then a return within the trailing 60 days, with a first-touch guard; the numerator is a subset of the denominator by construction.
- Volume and intensity: practiced user-days lead; rows per user-day is a ratio of totals over the range, never a mean of daily ratios.
- App Health: an equal-weight mean of five sub-scores (prayer reach, reading reach, journal reach, lectio depth, weekly return); a sub-score with a denominator under five is nulled, the composite is suppressed under three survivors, and a caveat shows under 30 users.
- Premium is paid or comped or creator, a documented mirror of the app's entitlement service with its own check script.
- Subscription transitions have one reader; sandbox purchases are excluded; "first paid" is the earliest trial conversion or direct purchase. The paywall funnel is sequenced per person and iOS only.

**Timezone.** Activity rows carry a user-local date column written in the user's own timezone, so one instant lands on different calendar days for different users, and filtering that column with fixed bounds silently drops users east of UTC. The dashboard filters only on true timestamp columns and buckets with a `dayKey` helper in Pacific time (`lib/analytics/timezone.ts`, with the rule restated in CLAUDE.md). A grep for range filters on the local-date columns in routes and non-demo library code finds none.

**Internal exclusion.** One `where` fragment (roster emails, creator flag, admin flag, signup-canary accounts) is resolved to ids and applied by default in production only; elsewhere it returns empty so staging is not blank. PostHog reads carry the same filter in-query, then anonymous sessions are dropped and the drops counted.

**Annotation markers.** `lib/analytics/deploy-markers.ts` holds 25 dated constants in code, not a table, each with a Pacific day, a short label and a long note, marking days when a definition or product change moves a metric without a behavior change (the Act hero, the refocus strip, the front door, the presence definition, the analytics canon, weekday reads counting, lectio catch-up, the onboarding step renumber, the activity ledger, direct purchase, and others). They are display-only: a dashed reference line on time series, a chip on aggregate cards, and the full note printed once in a "Notes on this view" strip listing exactly the markers the mounted widgets registered. Nineteen are referenced by the UI; four are imported nowhere.

**Demo mode.** `lib/analytics/demo`, 39 files, 10,158 lines. Switched on with `?demo=1` on the page; the fetch wrapper forwards it; each route forks after `requireAdmin` and before its first query and answers with a demo header. Twenty-six builders in `demo/routes` mirror the real routes as synchronous pure folds over one synthetic world whose event stream mirrors the presence legs, so widgets reconcile with each other. The clock is frozen at 2026-09-30 15:42 Pacific. Generation uses a seeded random generator with named substreams, five user archetypes, a Sunday peak, generated names, `example.com` emails and generated church names; the demo exclusion roster is empty. `scripts/check-analytics-demo.ts` pins the guard order per handler, that no demo file imports the database or the PostHog bridge or reads the wall clock or `Math.random`, installs a Prisma stand-in that throws on any access before modules load, runs every builder for the 7, 14, 30 and 90 day presets, asserts byte-identical output on repeat and on a rebuilt world, checks reconciliation identities, and server-renders every tab against demo payloads with no NaN or undefined. Wire parity with the real routes is weaker than it looks: only three builders import shared wire types; the rest are kept in step by hand, with the render pass as the net. This check is not in the type-check chain. Demo scale is an assumption block in `demo/world.ts` (about 5,000 accounts over 388 days); the captures show about 4,400 accounts and a DAU near 330, and those numbers are not Prava's.

**Capture and development session.** `scripts/capture-analytics.ts` (788 lines, `pnpm capture:analytics`) spawns its own local dev server, drives Playwright, refuses every non-demo and third-party request, fails if any dashboard response lacks the demo header, waits for charts to settle and crops with sharp. `lib/auth/dev-admin-session.ts` is a local-only admin session that requires five conditions at once (development mode, not on the hosting platform, a 32-plus character per-run token in the environment, the same token in a request header, loopback host), is honoured in exactly two seats, uses a user id that matches no row, and is refused by `next.config.js` in production builds. `scripts/check-dev-admin-session.ts` pins all of this and is in the type-check chain.

### The hard parts

1. **One meaning of "active".** The September discovery found several hand-rolled definitions and three retention definitions. The fix is the presence module plus a one-consumer rule enforced by `scripts/check-analytics-presence.ts`, which fences ten models behind the module with a now-empty allowlist and a self-test that the detector fires. A senior engineer would ask why a source scan instead of types, why the union lives in application code rather than a SQL view, and what the eight-leg fan-out costs.
2. **Timezones.** Commits on 2025-11-22 ("fix timezone issues") and 2026-05-19 ("fix analytics timezone bug", then the shared helper) mark the cost. Open questions: why Pacific rather than UTC, how DST is handled, and the explicit handling in `presence.ts` of a date read back as UTC midnight shifting a day.
3. **Definition change versus real change.** `analytics-dau-investigation.md` (2026-08-20) attributed a DAU drop to stacked causes (metric narrowing, removed surfaces, a catch-up feature compressing return days, fewer pushes), ruled out two hypotheses from code, and found every marker still carried a placeholder date. Its data pull was blocked, so the verdict is code-side only. Builds 7 and 8 dated the markers. The question is why history is kept broken at a dated line instead of backfilled.
4. **Joining two stores.** Events exist only from updated app builds, so event-to-database ratios understate. Approach: join at the user level, partition anonymous ids by id shape, filter the roster in-query, count the drops, degrade to an "unavailable" state. Questions: cache staleness and identity merging.
5. **A demo mode that cannot leak.** See the checks above. Questions: why generate rather than anonymize real data, and how drift is caught (partly by hand).
6. **An auth bypass that cannot ship.** Five conditions, build refusal, counted seats, 27 expectation sites. Question: why not a seeded local admin user.
7. **Small-sample honesty.** Floors, suppression, subset-by-construction comeback, totals ratios.

## 3. Lectionary authoring tool

### What it is

The lectionary tool at `/admin/lectionary` is where the appointed scripture readings for each Sunday and weekday are authored for two lectionary systems, the Roman Lectionary for Mass and the Revised Common Lectionary, along with per-reading teaching notes, responsorial psalm refrains and a per-week theme. It stores citations as structured verse ranges, pulls the text per Bible translation into a cache at write time, and reports how many upcoming weeks are fully servable. Access is the shared admin gate (ten of eleven handlers use the fresh re-read), and the sibling teaching cockpit's header says it is owner-only, so the same is inferred here. Forty-five files outside the module import from it: the home API (week theme, day identity line, opening psalm), the week and day lectionary APIs behind the Home Today card, the This Sunday card and the reader, the morning push (which sends the day's readings Tuesday to Saturday), the app-open screen, onboarding readings, the public landing page's live week (citations only), the weekly reflection's week context, read history, and the Bible coverage and read-record services. Serving is "sparse first": a day with nothing authored returns a null envelope and the Home section does not render. Without the tool the product would degrade to no daily readings, no week theme (falling back to legacy verse columns) and no readings push, rather than erroring.

Two neighbours are separate tools that share machinery: `/admin/memory-verse` (weekly verse authoring with a draft, approved, live lifecycle and version history, sharing the Sunday calendar engine, translation pool, provider layer and a containment indicator that says whether the weekly verse sits inside that week's readings) and `/admin/teaching` (per-denomination doctrinal topics, an unrelated data family).

### Architecture

**Routes.** The admin UI is one page and four components: the list with the coverage horizon, a quick-add sheet for a whole Sunday or day set, a per-reading edit sheet, and a week theme sheet. The admin API is 10 route files with 11 handlers: collection list and quick-add create; per-reading patch; per-reading AI teaching draft; per-reading text fetch; authoring horizon; batch RCL rights flip; text coverage summary; per-translation bounded fetch-all; week theme save; week theme AI draft. The user API is five route files: week envelope, day envelope, mark-read for each, and read-record detail.

**Data model.** `LectionaryReading` carries tradition, Sunday cycle, weekday cycle, reading slot, slot order, exactly one of six key idioms, a derived slot key, display citation, teaching text and label, response line, a rights-cleared flag and an active flag, under a seven-column compound unique. `LectionaryReadingSegment` holds ordered contiguous verse ranges with display-only half-verse suffixes. `LectionarySegmentText` caches text per segment per translation with verse boundary offsets. `LectionaryFetchFailure` records only currently failing fetch units and is deleted on success. `LiturgicalWeekTheme` is keyed by the opening Sunday's slot key and holds the theme and two teaching registers. `LectionaryReadRecord` and `DailyReadingRecord` hold user read marks. There is deliberately no draft or published lifecycle and no version table: rows cite a fixed external source, so active plus rights-cleared is the whole lifecycle (schema comment).

**Authoring.** The quick-add sheet offers seven key idioms (season week, feast, RCL Proper, weekday, sanctoral proper, common, RCL daily), takes citations typed as a missal prints them, and saves the set in one transaction; Ordinary Time weekdays show paired Year I and Year II fields beside one Gospel. Live parsing in the browser uses the same `citation-parser.ts` module the server runs authoritatively. A duplicate slot returns a conflict with the existing rows so the sheet flips to edit mode. The horizon panel is an entry point: clicking a missing unit opens the sheet pre-filled. Two AI drafters (per-reading teaching, and a week theme from all four Sunday readings) return a draft without persisting; only Save writes, and both send only public-domain WEB text to the model and error if it is not cached. Bulk ingest (`scripts/ingest-lectionary.ts`) validates every snapshot file first, collecting all errors, then idempotently upserts on the compound unique; `scripts/export-lectionary.ts` writes deterministic snapshots.

**Validation.** `dataset.ts` does a structural parse where each idiom branch is strict (a row with two idioms matches none), then semantic checks for tradition, track and feast consistency, segment contiguity, book and reference validity, and in-file duplicates; the editor and the ingest share this one path. The citation parser has a strict grammar, parses the whole string or lists every error, and refuses whole-chapter citations, "or" alternatives and bracketed optional verses. `feasts.ts` rejects rows keyed on a feast the resolver never emits for that tradition (they would sit dark forever). Snapshot round-trip, phrase and boundary checks are listed under scale.

**Serving per tradition and week.** Traditions are Roman and RCL (RCL serves the complementary track only). `tradition.ts` maps each denomination to an ordered candidate list as a total record: Catholic to Roman; four mainline traditions to RCL only; low-church and unknown to RCL with Roman fallback; Eastern Orthodox to none, on purpose. For Sundays, `slot.service.ts` wraps the frozen Sunday engine (`liturgical-calendar.ts`: computus, Advent, Baptism of the Lord, season and week, the A/B/C cycle from Easter year modulo three) and emits one of three idioms (season plus week, feast, or RCL Proper by date window). For weekdays, `day-engine.ts` builds a whole liturgical year keyed by Easter year, resolves collisions on a 13-level precedence scale, runs a solemnity transfer pass and memoizes; `day-route.ts` turns the winning celebration into a proper, ferial or common key; RCL weekdays route through an anchor-Sunday resolver (Monday to Wednesday look back, Thursday to Saturday look forward). Cycles are Sunday A/B/C and Roman weekday Year I/II, each with a NONE value, read with two-value IN filters that prefer exact over NONE in memory. Fallbacks: the first servable tradition candidate wins; an unservable day or week is null; text falls to the WEB floor per reading and is never mixed inside a reading; the week theme falls back to legacy verse columns; uncleared rows are silently invisible. Text is fetched only at write time from the provider layer; the read path never calls a provider. Seven translation codes are seeded (WEB, KJV, BSB, ESV, NKJV, NLT, CSB) and a weekly cron lane re-fetches stale text. There is no server-side cache on these paths; edits reach users when the client's five-minute stale time lapses, and the day query key carries the date so a midnight rollover cannot show yesterday's set.

**Environments.** `pnpm lectionary:sync:prod-to-staging` chains a production export (read-only) into a staging import with prune. The archive is NDJSON with header, rows and trailer; rows are matched by natural key, never by id; counts are verified after the run. `scripts/content-transfer/manifest.ts` classifies every schema model as carried or refused, and its check fails if a new model is unclassified, if a carried model references users, or if a carried column name looks like an asset URL. Import refuses same-host transfers, requires an extra flag for production, prints the prune list and asks again.

### The hard parts

1. **A date is not a liturgical identity.** Trinity Sunday lands on a different Ordinary Time week each year; Christmastide week numbers mean different Sundays in different years. Approach: three Sunday key idioms, Christmastide fully feast-keyed, engine-keyed Christmas rows rejected by the validator. A senior engineer would ask why not store dates; the answer is that rows are year-independent and reused every three years. Evidence: the slot service header, the feast enum comment, and a totality sweep in `check-lectionary-slot.ts` of every Sunday from 2026 to January 2034 for both traditions.
2. **Weekday precedence and transfers cannot be computed per date.** "Nearest free day" needs the whole year's occupancy, so the year is the unit of computation, with a total-order precedence table and transfer rules as data. Correctness is pinned against published ordo dates (Joseph 2008, Annunciation 2016, Immaculate Conception 2024, John the Baptist 2022) and `check-liturgical-day-engine.ts` reports 9,002 assertions including exactly one winner per day. Honest caveat: the precedence and transfer tables carry banners saying they are unverified pending the owner's missal pass, and memorials are documented as partial.
3. **The commons routing bug.** Fifteen memorials once routed to shared "common" sets, so seven martyr days shared one slot and a hand-fix for one date became every other martyr's readings. The 2026-09-15 ruling routes memorials to the weekday's readings and the slot check asserts zero common-routed days; the commons machinery is kept as a deliberate future option. Evidence: a comment in `sanctoral.ts` and the "fix roman calendar" commit of 2026-09-16.
4. **Uniqueness across nullable key shapes.** Postgres treats NULLs as distinct in unique indexes, so nullable discriminators left rows un-deduplicated. Approach: required enums with NONE values and one derived slot key built by a single function. Evidence: schema comments on the track, cycle and reading models.
5. **Text acquisition under a provider cap.** Bounded, resumable slices; work derived from what is missing rather than a stored cursor; serial calls with spacing; a daily budget below the provider cap; exponential backoff that gives up after eight attempts; error class stored, never message; a re-fetch returning different text keeps the cached text. A no-op Save once wiped cached text through the segment cascade and was fixed with a segment fingerprint guard (2026-07-28).
6. **Content sync that cannot carry user data.** The manifest gate above, with 123 assertion sites.

A good secondary story: "Ready means servable". The horizon's Ready state requires an active row, parseable segments, floor text for every segment and rights cleared, computed in four database statements because the staging pool is one connection.

## 4. Commitment library

### What it is

The commitment library is the admin content system for the Act pillar (backend name "serve"). Residue of a past multi-reviewer design remains (vote endpoints, a submissions model, submitter and reviewer columns); the "content viewer" permission was stripped on 2026-02-27, and git shows one author.

The honest status: the authoring tool is intact and reachable, but the user-facing consumer is not in the current client. Commit f40a73fb "Phase 2, The Strip" (2026-07-16; 92 files, 523 insertions, 17,205 deletions) removed the whole Act client surface: the acts library, the acts-today components including the zero-history floor, the act workspace, the act logging flow, the home step tracker, the onboarding act selection screen and the acts library page. ### Architecture

**Routes.** The admin UI is 20 files and 11,687 lines including 1,241 lines of scoped CSS: one page mounting a TanStack table library view (2,003 lines) with modals for create (1,033), edit (1,059), view, preview as a user card, delete, deny with notes, manage buckets, manage review campaigns, bulk JSON import, bulk image upload, duplicate checker, profile simulator (1,963), an in-app user guide including a tag strategy, a step editor and a theme toggle. The target profiles page (370 lines) lists saved profiles with status counts and a status dropdown. The API is 28 files and 4,006 lines across four groups: commitments (list with filters, create, get, patch, delete, approve, deny, vote, image presign and confirm and delete, bulk upload presign, bulk import as an all-or-nothing transaction, bulk delete, export honouring filters, AI enhance, AI step generation, find and dismiss duplicates, library, pending count, legacy submissions, a one-time act-category backfill), buckets, target profiles and review campaigns.

**Data model.** `CommitmentOption` is the library row: a category enum, an eight-value biblical act category, difficulty (easy, medium, hard, difficult), estimated minutes, title, description, prompt and guidance, image fields, and the personalization taxonomy: focus area, settings, time preferences, required contexts (all must match) and optional contexts (any may match), personality fit, gender fit, target faith journeys, target age ranges, tags, required activities (a hard gate) and preferred activities (a soft boost), church flags, source (curated or user-submitted), approval workflow fields including whether the last edit requires review, review stamps, and an active flag. `ActStep` holds ordered authored steps (zero steps means a one-step act). `ContentBucket` with a junction table groups content. `TargetProfile` stores profile arrays plus captured metrics (eligible count, average score, high-scorer count) and a four-value status. `DismissedDuplicate`, `ReviewCampaign` with per-commitment review status, `CommitmentVote` and the legacy `CommitmentSubmission` complete the authoring side. The runtime side is `DailySelection` (per user per day: one pray id, four serve ids, the chosen serve, refreshed-at), `DailySelectionLog` (one analytics row per shown item with the score breakdown and a denormalized snapshot of the user's profile), `UserProgression` (serve completions per difficulty and a phase from one to three), `CommitmentLog`, and `ActCommitment` with events for persisted multi-step acts.

**Authoring and validation.** Create and edit expose category, difficulty, estimated minutes, act category, title, description, guidance, steps, tags, personality fit, gender fit, target faith journeys, target age ranges, focus area, settings, time preferences, required and optional contexts, and buckets. Every write is validated with Zod against the Prisma enums; bulk import coerces nulls to defaults and reports per-row index, title and error. Server rules: editing an approved row resets it to pending; difficulty is re-validated when the category changes; a structural change to steps (count or order, detected by comparing step ids position for position) on an act that users are midway through requires an explicit acknowledgment flag because progress is stored as integer indices. AI enhance (748 lines; Anthropic SDK, model tier from the shared registry, the system prompt cached with a cache-control block, usage recorded to the token ledger) takes a rough idea plus optional category, hints and a target profile, injects 75 to 100 recent titles for duplicate avoidance, and returns JSON that pre-fills the modal. Step generation drafts up to six steps from unsaved form data. The duplicate finder sends all approved serve and pray rows grouped by category to the model, asks for high and medium pairs with reasons, and filters previously dismissed pairs. The library has its own light and dark toggle scoped by a root attribute so it does not collide with the user app's theme, with 65 CSS custom properties.

**The selection algorithm, step by step.** It runs server-side on the first daily request and is cached in `DailySelection`.
1. If the user has an active persisted multi-step act, it is returned as the sole serve entry and suggestions pause.
2. Otherwise, on a cache miss, pray and serve selection run in parallel; scripture is null (the old model was retired).
3. Eligibility comes from one predicate, `algorithmEligibleWhere` in `commitment-eligibility.ts`: approved, active, curated (approved user-submitted acts are browse-only, never auto-served), not church-specific, and no seasonal tag in any casing because tag data is case-inconsistent.
4. The pool splits into universal (no required or optional contexts) and personalized.
5. Serve fills four slots as two personalized plus two universal. Each pool's difficulty distribution follows the user's progression phase (phase one easy and medium; phase two pushes personalized to medium and hard; phase three hard and difficult; universal always stays accessible), with phase one further keyed by the onboarding act frequency. Phase advances at five medium or three hard completions.
6. Repeat avoidance excludes ids completed in the last 14 days (personalized) or 7 days (universal), everything shown yesterday, and on refresh the currently shown set.
7. Scoring applies hard gates first (life context all-or-any, church membership via the faith-journey signal, age range, gender-only flags, required activities); any failure scores zero and drops. Then a weighted 0 to 100 sum: act-category affinity 25 percent, personality and connection 20, barrier avoidance 20, focus-area affinity 15, faith-journey fit 10, gender fit 10, multiplied by an activity-overlap factor of 1.0, 1.2 or 1.3.
8. Penalties: shown but not chosen in the last 30 days subtracts three points per event, capped at 30 with a floor of one. Pray adds an exponential completion-recency decay with a 14-day half-life and up to 70 percent reduction over 60 days.
9. Pick: sort by score, randomize ties within five points; per slot, 85 percent take the top scorer and 15 percent take a random other for variety. The fallback chain is same difficulty in the other pool, then other difficulties, then the unscored legacy random path, which now re-applies the hard gate through `act-gate-eligibility.ts`.
10. A diversity nudge: if all four share one act category, swap the last for a gate-passing candidate from another category. Final order shuffled.
11. Pray: a 60/40 coin flip picks universal or personalized as the primary pool, same scoring, falling back to the other pool and then to ignoring recency.
12. Everything shown is logged with its score breakdown, fire-and-forget.
13. Premium gating: refresh is once a day (creators exempt) and three a month for free users, unbounded for premium; the library browse endpoint gives free users a capped six-item teaser. Randomness is plain unseeded `Math.random` on the server; only the admin simulator uses a seeded generator so re-rolls reproduce, and the diversity swap accepts an injectable generator for tests. The "zero-history floor" was a purely presentational client component with no server logic and was deleted in the Strip.

### The hard parts

1. **Keeping the simulator honest with the server.** The simulator imports gate and scoring functions from the personalization service (which has an explicit block of exports for client-side scoring) but hand-mirrors recency windows, decay constants and phase distributions.
